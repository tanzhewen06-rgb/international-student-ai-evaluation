# 实验记录说明

在回答生成代理的 `main.py` 中修改 `MODEL_NAME`、`BATCH_NAME`、`REPEAT_COUNT`、`PERSONA_FILE`、`STUDENT_BACKGROUND_FILE` 和 `SCENARIO_FILE`，然后直接运行。当前有五个情境，每个重复一次时共发起五次生成请求。每次运行产生新的 `run_id`，每次尝试产生唯一的 `response_id`。每次请求结束后立即保存记录，包括失败记录。

## 第二版紧凑存储格式

每个批次中，每个回答模型分别保存一个 `responses_<完整模型编号>.jsonl` 文件。每个非空行都是一个完整 JSON 对象，整个文件外层不使用 JSON 数组。

- 第一行的 `record_type` 为 `metadata`，`schema_version` 为 `2`。其中的 `common` 对象只保存一次完整角色设定及其哈希值和来源、模型、批次、生成参数及逻辑记录格式版本。`scenarios` 对象只保存一次各情境的完整内容、名称和哈希值。`user_prompt_prefix` 保存精确前缀：旧输入为 `Scenario:\n`，启用背景时则在情景标签之前包含学生背景块。`common` 中可选的四个 `student_background_*` 字段共同保存文件名、版本、完整原文和哈希值；字段不完整或内容不一致会被拒绝。
- 后续各行的 `record_type` 为 `response`，保存 `response_id`、`run_id`、协调世界时时间戳、`scenario_id`、重复序号、完整 `response_text`、成功或失败状态、耗时和错误信息。模型与批次信息从元数据头继承，不在每条回答中重复存储。

两个正式代理共用 `record_format.py`。它重建每条完整逻辑记录，包括原始角色设定、情境、用户消息、模型和参数。用户消息由已保存的前缀和情境拼接而成，不会概括、规范化或换成当前文件中的提示词。

包含二十五次尝试的文件因此有二十六个 JSON 对象：一个元数据头和二十五条回答。元数据头不算回答，也不发送给评委。不能把这二十六个对象都当作独立回答。

## 重复运行

同一模型在同一批次重复运行时，追加回答行并保留已有元数据头。在调用模型前，程序检查元数据头是否与本轮读取的角色设定、全部情境、生成参数及来源一致。修改提示词或参数后，必须使用新批次。

程序拒绝向旧式完整记录文件追加紧凑记录，也拒绝向最后一行不完整的文件追加内容。每个文件的锁用于避免两个生成进程同时写入。只有确认上一次进程已经停止后，才能清理遗留的 `.jsonl.lock` 文件。

每次执行开始时重新读取提示词文件。`main.py` 管理运行配置和模型调用，`storage.py` 管理记录保存。回答生成代理不产生评分。正式评分结果单独保存在相邻正式评分代理的 `evaluations` 目录中，按评委、回答来源和独立运行分组。

转换不调用模型，不生成新回答或分数。正式评分代理既支持旧式格式，也支持当前紧凑格式。空评分文件和报告模板只是占位文件，不代表已有评分结果。

## 适用范围与失败处理

紧凑格式减少保存文件中的重复文本。每次模型生成仍会发送所需的完整角色设定和情境；仅压缩保存格式不会减少接口的输入令牌用量。生成参数对象为空时，使用模型接口默认值。现有仅返回文本的客户端不报告服务端模型版本、令牌用量或费用。密钥不会写入记录。

控制台显示进度和保存路径；完整回答和请求错误详情在记录文件中。请求失败后保存错误，不自动重试，并继续其余情境。磁盘写入失败会停止运行。如果有任何请求失败，结束时返回非零退出状态。

当前入口选择 `international_student_scenario_prompts V2.md`，配合顾问角色第二版、学生背景第一版，输出到 `batch_003`。情境文件名和版本信息跟随实际选择的文件保存，无需另设版本开关。

提示词文件集中保存在回答生成代理的 `prompts` 文件夹中；`SCENARIO_FILE` 仍只需要填写文件名。
